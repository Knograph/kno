# Validate: the holdout stage

v0.2's centerpiece. Every v0.1 report carries `- **not yet validated on holdout** — validate is
not in this release; this is a selection-time estimate, winner's-curse inflation included`
(`cli/report_render.go:119-121`) and `"validated_on_holdout": false`, hardcoded at
`cli/jsonreport.go:508`. Validate is what makes those two lines stop being permanent.

`core/seal.go:34-38` states the pre-condition this plan exists to discharge:

> Every stage before Validate takes the result. Validate reads the holdout through a separate
> path that does not exist yet — deliberately. Designing how a holdout is legitimately opened,
> and who may do it, belongs with the stage that needs it, not three milestones early against a
> token nobody can meaningfully gate.

This plan is that design. It is written against the tree at `4622b90`; every schema field,
function name and constant below was read before it was written.

**Phase-1 re-reviewed 2026-08-31 — verdict: amend; amendments applied.** Four things changed,
and four claims that were reasoned rather than checked are now settled fact with the hedging
deleted: `errs.ErrHoldoutSealed` is referenced from `core/errs/errs_test.go` and from nothing
else, so §2's third property really is its first caller; `cli/baseline.go:422` calls
`core.Baseline(ctx, core.Seal(evals), opts)` against a `*SealedEvals` parameter, so no baseline
path can reach a holdout Case today and criterion 5's canaries guard a property the type system
already holds; `split.MinHoldout = 20` and `Counts.Underpowered()` is
`Holdout > 0 && Holdout < MinHoldout`, exactly as §8 and criterion 16 assume; and
`Guard.Restore`'s godoc requires the call precede any `Authorize`, which `core/value_loop.go`'s
`openRun` already does — §4 inherits that ordering rather than inventing it. The dominant
finding is a correctness bug in this plan's own test spec: the AST test as first written would
have **failed on a correct implementation**, because `openHoldout`'s declaration is itself an
occurrence of the identifier `openHoldout` — it now counts call expressions and asserts a count
per file *(F1)*. The precedent claim for that test is withdrawn: it does not share
`core/boundary_test.go`'s import-graph mechanism and must not inherit its reputation for
robustness *(F2)*. The unexported-type guarantee is narrowed to what Go actually promises —
unconstructible, not un-holdable — and a fourth AST check closes the interface-forwarding hole
*(F3)*. The two-arm cost doubling gains the weighing it lacked, including a cached-control-arm
design that would halve the marginal cost of repeat validations, deferred with its reasons
*(F4)*. Confirmed sound and not reworked: the identifiability argument against a dev baseline,
the deliberate absence of `stats/portfolio.Correct`, and one-shot-recorded-at-start, whose test
is sharpened to drive a kill **before** the first Case as well as mid-run *(F5)*.

**Conflict with DESIGN.md, flagged rather than silently resolved (CLAUDE.md, opening
paragraph).** `DESIGN.md:88` says Validate "confirms the aggregate gain, **catches pairwise
poison**, and produces the number you're allowed to put in a slide", and `report.proto:89-95`
reserves `interaction_penalty_detected` / `suspect_interactions` for it. This plan ships the
first and third and **does not ship pairwise poison detection** — see §7. That is a scope
reduction against DESIGN.md and it needs an explicit decision, not a quiet omission.

## Problem

Four things are missing, and they are not independent.

1. **No holdout read path exists anywhere.** `core.SealedEvals` filters *to* `SPLIT_DEV`
   (`core/seal.go:75`); there is no inverse and no second constructor. `errs.ErrHoldoutSealed`
   (`core/errs/errs.go:54-58`) is declared and returned by **no non-test code** — the seal is
   enforced by the type system, not by that error.
2. **No stage can consume a Portfolio as a set.** Every `ContextInjector` implementation
   refuses a second Asset: `openaicompat`'s `injectable` returns `ErrInvalidInput` with
   *"this Agent already carries an injected Asset"* (`adapters/agent/openaicompat/context.go:64-71`),
   and `bedrock`, `anthropic`, `vertex`, `fake` mirror it. `WithContext(a *Asset)` takes one
   Asset. A Portfolio is a set. Nothing bridges that today.
3. **There is no recorded holdout baseline to compare against.** `core.Baseline` takes a
   `*SealedEvals` (`core/baseline.go:328-331`), so `BaselineResult.AggregateScore` is a
   **dev-only** mean. Validate cannot pair a holdout treatment score against it.
4. **Validate's output has nowhere to land.** `store.Store` (`store/store.go:39-196`) has
   `WritePortfolio`/`Portfolio` and `WriteGaps`/`Gaps` and no report or validation methods;
   `store/sqlite.go` has `portfolios` and `gaps` tables and no third. `knov1.Report` is aliased
   at `core/types.go:54` and **constructed nowhere outside `gen/`** — verified by grep.

And one thing that is a hazard rather than a gap: **the holdout is consumable exactly once per
portfolio, and nothing in the system knows that.** `docs/mental-model.md` already promises the
user "the Portfolio meets it exactly once, at Validate". Today that is prose. After this plan it
is a durable record with a refusal attached.

## Design

### 1 — What validate measures, and against what

**Decision: a paired, within-run, two-arm contrast on the holdout.** Validate runs the holdout
Cases twice — a **control arm** with the un-injected Agent and a **treatment arm** with the
whole context-destination Portfolio injected — and reports the mean paired difference with its
interval.

```
holdout_gain = mean over holdout Cases of ( score(treatment, c) − score(control, c) )
```

sign-corrected by `Goal.Direction()` exactly as Value does, and interval'd by
`interval.PairedTrials(perCase, o.Goal.Domain(), interval.DefaultLevel)`
(`stats/interval/interval.go:81`) — the call whose shape derives the pair count structurally, so
the sqrt(k) trial-narrowing bug is unrepresentable.

**Why not against the recorded Baseline.** It is not available. `core.Baseline` is handed a
`*SealedEvals`; no baseline run has ever scored a holdout Case. Comparing a holdout treatment
score against the dev baseline mean would produce
`portfolio effect + (holdout − dev population difference) + provider drift between two runs`,
three terms with one number. The dev/holdout split is a hash of the Case ID
(`split.AssignSplit`, `adapters/evals/split/split.go:52`), so the population difference is
*random*, not zero — at `MinHoldout = 20` it is easily larger than any portfolio effect. That
estimand is unidentifiable and the option is rejected on correctness, not cost.

**Why not a separate `kno baseline --holdout` run as the control.** It would move the
seal-break into Baseline — the wrong stage, and the one every existing canary test asserts
cannot see the holdout. It also puts a wall-clock gap between the arms, and
`docs/what-the-numbers-mean.md:47` already names provider drift as a source of error no interval
covers. Rejected. (It is, however, the right shape for v0.3's `validate --agent tuned:<ref>`,
where the two arms are two *agents* over one recorded holdout and the drift is the thing being
measured. §12 keeps the door open.)

**What the claim is, stated for the docs page:** *"With this Portfolio in context, the agent
scored X better on N Cases it had never been measured on, 95% CI [lo, hi], under context
injection — an upper bound on what retrieval would deliver."* The last clause is
`docs/what-the-numbers-mean.md:106` ("Context injection is an upper bound") and it does not stop
applying because the slice changed.

**Cost consequence, stated up front because it is the design's main price:** two arms means
`2 × n_holdout × trials` agent invocations. At `MinHoldout = 20`, `trials = 1`, that is 40 calls.
This is cheap in absolute terms and it is exactly double the naive expectation, so the consent
quote must show the doubling explicitly (§4).

**How much of that doubling is avoidable, and why this plan still pays it** *(F4)*. The
identifiability argument above establishes that the control arm is *necessary*; it does not make
the price *unweighed*, and review was right that this plan quoted a 2× without ever asking who
declines it. The numbers: at `MinHoldout = 20, trials = 1` the doubling is 40 calls against 20 —
cents on every scheme `docs/status.json` marks `spends: true`, and nobody declines that quote.
The figure that could plausibly change a mind is the routed scale: a 400-Case eval set at
`split.DefaultHoldoutFrac = 0.2` (`adapters/evals/split/split.go:28`) yields ~80 holdout Cases,
so `trials = 3` is 480 calls against 240. Set beside `DESIGN.md:361-364`'s $15–40 valuation run,
validate's second arm is a rounding error on the pipeline — the stage is cheap because it runs
the Portfolio once, not once per Asset. The consent dialog still quotes the doubling in full,
because prime directive 4 is about disclosure, not about magnitude.

**The middle design review named, considered and deferred: cache the control arm per eval
fingerprint.** The control arm is the un-injected Agent over the holdout, and it **does not
depend on the Portfolio at all**. A first validate could record its control measurements keyed on
`(eval_fingerprint, agent_ref, resolved_model, trials)`, and every later
`--allow-repeat-holdout` validation of a *different* Portfolio could replay them as its paired
baseline — halving the marginal cost of the second and subsequent validation (40 → 20 calls at
`MinHoldout`; 480 → 240 at the routed scale) **without** reintroducing the confound this section
rejects, because the cached control is still a holdout measurement, merely not a fresh one.

**Deferred rather than rejected, for three reasons in damage order.** (a) It breaks the
within-run pairing that makes the interval honest. A replayed control arm is separated from its
treatment arm by wall-clock and by the provider drift `docs/what-the-numbers-mean.md:47` names —
which is *precisely* the objection raised below against `kno baseline --holdout`. Accepting it
here to save cents while rejecting it there on principle would be incoherent. (b) It pays only on
the second and later validation against one holdout, which §3 already treats as the discouraged
path; optimizing the path the design discourages is the wrong order of work. (c) Its
cache-invalidation rule spans the agent ref, the resolved model and `trials`, and a stale-control
bug does not crash — it produces a **wrong headline number**, in the one place this product
promises a right one. The saving is real and small; the correctness surface is real and not
small. Ledgered with a trigger (§Accepted risks).

### 2 — How the seal opens

This is the security-boundary decision. **Decision: the holdout opener is package-private to
`core`, its type is unexported, and the CLI never holds a holdout iterator at all.**

```go
// core/holdout.go
type holdoutEvals struct{ inner Evals }          // unexported: unconstructible outside core
func openHoldout(e Evals) (*holdoutEvals, error) // unexported
func (h *holdoutEvals) Cases(ctx context.Context) (iter.Seq2[*Case, error], error)
```

`Cases` is `SealedEvals.Cases` with one line changed: `SPLIT_HOLDOUT` passes, everything else —
`SPLIT_DEV` and `SPLIT_UNSPECIFIED` alike — is skipped. The unassigned-split filter is kept for
the mirror-image reason `core/seal.go:54-57` gives: a Case with no split has not been through
ingestion, and admitting it to the holdout inflates the denominator of the only number that
belongs in a slide.

`ValidateOptions.Evals` is a plain `Evals`. `core.Validate` calls `openHoldout` itself. Three
properties follow, in decreasing order of strength:

1. **`cli`, `tui`, `api` and every external consumer cannot *construct* a holdout reader.**
   Not "must not" — cannot. The type and the constructor are both unexported, and Go leaves no
   way around that: another package cannot name the type, cannot build one reflectively, and
   cannot produce one with a composite or interface literal. This is stronger than the seal's
   guarantee (which is a *requirement* to wrap, discharged by discipline at the call site) and it
   costs nothing.

   **That guarantee is exact for construction and narrower than it first reads for exposure**
   *(F3)*. "Cannot construct" is not "cannot hold or use". Interface satisfaction is indifferent
   to whether the concrete type is exported, so if any exported `core` function, event field or
   callback ever returned an `Evals` **interface** value backed by a `*holdoutEvals`, a caller
   outside `core` could call its exported `Cases` method and read the holdout without ever naming
   the type — and the signature check below, which matches `*holdoutEvals`, would see only
   `Evals` and pass. **The invariant this plan commits to is therefore stated positively: no
   exported function, method, struct field, event or callback in `core` ever returns or forwards
   a holdoutEvals-backed `Evals`.** The value is constructed in `openHoldout`, consumed inside
   `core.Validate`, and never escapes that call. The fourth AST check below is what keeps that
   true over time; the type system alone does not.
2. **Inside `core`, exactly one call site.** Enforced by a test, named below.
3. **`errs.ErrHoldoutSealed` finally gets a caller.** `openHoldout` type-asserts its argument:
   handed a `*SealedEvals`, it returns `ErrHoldoutSealed` rather than iterating one and yielding
   nothing. This matters because a sealed source passed to validate would otherwise produce
   *zero holdout Cases*, which is indistinguishable in every downstream surface from "your eval
   set has no holdout" — a silent, plausible, wrong answer, which is the exact failure mode
   `core/seal.go:54-57` and `split.Counts.Validate` are both built to prevent.

**The test that proves no other stage can take the same path: `TestOnlyValidateOpensTheHoldout`,
in `core/holdout_boundary_test.go`.**

**It does not inherit `core/boundary_test.go`'s robustness, and this plan no longer claims it
does** *(F2)*. That test shells out to `go list -deps` and asserts over the **import graph** — a
coarse, total relation that is hard to fool and impossible to half-satisfy. This one parses
`core`'s own non-test files with `go/ast` and reasons about occurrences **inside** a single
package, where the import graph says nothing at all. Different technique, different failure
modes: an AST walk can be evaded by an alias, a method value, or a wrapper it does not model, and
it is the walk itself — not the toolchain — that has to be reviewed. It is worth having anyway,
because nothing else can catch a second in-package call site, but it is a bespoke test carrying a
bespoke risk (§Accepted risks).

**And it must count call expressions, not identifier occurrences** *(F1)*. The declaration
`func openHoldout(...)` in `core/holdout.go` is itself an occurrence of the identifier
`openHoldout`, so the naive spec — "referenced in exactly one file, and that file is
`core/validate.go`" — **fails on a correct implementation**. That is worse than a merely wrong
test: the cheapest way to turn it green is to loosen the walk until it also stops seeing the
second call site the test exists to catch, converting a security boundary into a formality. The
spec is therefore explicit about the node type and about every expected count:

- The walk visits `core`'s non-test files and counts **`ast.CallExpr` nodes whose `Fun` is the
  identifier `openHoldout`**, ignoring the `ast.FuncDecl` that declares it and any doc comment
  naming it. Expected: **zero** such calls in `core/holdout.go`, **exactly one** in
  `core/validate.go`, **zero** in every other file in `core`. All three counts are asserted, so
  deleting the call fails as loudly as adding one — and a walk that has been loosened into
  matching nothing fails too.
- No exported function, method or struct field in `core` has `*holdoutEvals` in its signature —
  the compiler already guarantees this for other packages, and this catches an accidental
  re-export within `core`.
- **The fourth check, closing the interface hole** *(F3)*: the test enumerates every exported
  function result, method result, exported struct field, event field and callback parameter in
  `core` whose type is the `Evals` interface (or a type containing one), and asserts the
  enumeration is **empty**. It is empty today. The PR that makes it non-empty fails, and its
  author must then prove the new outlet cannot be handed a `*holdoutEvals` — which is exactly the
  argument property 1 above needs a human to make, and exactly the argument the concrete-type
  signature check cannot make on its behalf.
- `grep`-equivalent over the whole module outside `core` finds no reference to `holdoutEvals`
  or `openHoldout`.

Removing the seal from `Baseline` or `Value` still fails their existing canaries
(`core/value_loop_test.go`'s planted-holdout-Case canary, `docs/plans/2026-08-26-value-stage.md`
P2-13). Those are kept and not weakened.

### 3 — One-shot semantics

**Decision: the holdout is consumed at the moment validate STARTS, recorded durably, and the
same (eval, portfolio) pair is never validated twice.**

Recorded via two new `store.Store` methods and one new table:

```go
RecordHoldoutUse(ctx context.Context, use *store.HoldoutUse) error
HoldoutUses(ctx context.Context, evalFingerprint string) ([]store.HoldoutUse, error)
```

```sql
CREATE TABLE holdout_uses (
  eval_fingerprint TEXT NOT NULL,   -- eval content hash + split seed + holdout_frac
  select_run_id    TEXT NOT NULL,
  validate_run_id  TEXT NOT NULL REFERENCES runs(id) ON DELETE CASCADE,
  created_at       TEXT NOT NULL,
  PRIMARY KEY (eval_fingerprint, select_run_id)
);
```

The row is written **before the first agent call**, in the same transaction that creates the
Validate Run. Three rules follow:

- **Same portfolio, same evals, prior run COMPLETED** → refused. `errs.ErrInvalidInput`, message
  naming the prior validate run ID, fix `read it with 'kno report --validate-run-id <id>'`. There
  is no flag. The number already exists; re-measuring it is not a new experiment, it is the same
  experiment run twice and reported once — which is p-hacking with extra steps.
- **Same portfolio, prior run INTERRUPTED / BUDGET_STOPPED** → a *fresh* run is refused with fix
  `--resume`; `kno validate --resume --run-id <id>` continues the same run. This is not a second
  peek: `Store.CompletedMeasurements` skips finished Cases, so the resumed process reads only
  Cases the first process never reached, and the interval is computed over the union exactly
  once. Recording the use at START rather than at completion is what makes this honest — a
  crashed validate *has* peeked at part of the holdout, and pretending otherwise is the leak.
- **A DIFFERENT portfolio against the same holdout** → allowed, **counted, and disclosed**.
  Requires `--allow-repeat-holdout`. `Validation.holdout_use_index` records the ordinal (1 for
  the first), the report prints `this holdout has now measured N portfolios; the interval below
  is NOT corrected for that`, and `--json` carries `holdout_uses: N`.

**Why not refuse a second portfolio outright.** Because the user would then delete `kno.db`, or
re-split with `--split-seed`, and get an *unobservable* second peek instead of a counted one.
Every mechanism in this repo prefers a labelled compromise to an unenforceable prohibition —
`split.MinHoldout`'s own godoc ("the Run still executes... but it is marked underpowered") is the
same judgement. The statistical truth is stated plainly rather than enforced: validating N
portfolios against one holdout re-introduces exactly the multiplicity the holdout existed to
remove, at rate N rather than at rate `n_screened`. Correcting for it is ledgered, not shipped
(§Accepted risks).

### 4 — Spend

Validate calls the agent over holdout Cases. Everything prime directive 4 requires applies, and
none of it is new machinery — the plan reuses what Baseline and Value already share.

- **The invoker.** `core.invoker` (`core/invoke.go:37-76`) is the authorize→call→settle→retry
  core, and its godoc enumerates six separately-discovered money defects it holds in place.
  Validate builds **two** invokers, one per arm, exactly as Value does (`core/invoke.go:39-41`
  names this case). It writes no third copy.
- **The estimate and the quote.** `ValidateOptions.Guard *budget.Guard`, constructed in
  `cli/validate.go` and driven through `consentDialog` (`cli/consent.go:98`) with the same
  `consentRecorder` handshake baseline and value use (`cli/baseline.go:307-397`,
  `cli/value.go:273-336`). The intent estimate is `2 × n_holdout × trials` calls priced by
  `Estimator.WorstCase()` where the adapter implements `Estimator` (`core/ring0.go:73`) and by
  `EstCostPerCallUSDMicros` otherwise — the same fallback ladder as Value
  (`core/value_loop.go:862-881`). **The quote must show both arms**: `40 calls (20 holdout Cases
  x 2 arms x 1 trial)`. A quote showing 20 understates by exactly 2x, which is the failure
  `core/ring0.go:95-104` records having already happened once at a different multiple.
- **Persistence and checkpointing.** Each measurement is written with
  `store.RecordMeasurement` — the Value-stage table, unchanged. `store.MeasurementKey`
  (`store/measurement.go:60-70`) is `{AssetID, CaseID, Arm, Trial}`; validate sets
  **`AssetID = the Select run ID`**. That is unique per portfolio, meaningful when read back,
  and means the `(run_id, asset_id, case_id, arm, trial)` primary key works unchanged. **No
  measurements-table schema change.** The recorded row is the done-marker, as everywhere else.
- **Resume.** `ValidateOptions.Resume` mirrors `core/value_loop.go:380-447`: on resume, load the
  Run, refuse a mismatched `input_fingerprint`, then
  `restored, _ := o.Store.SettledSpend(ctx, o.RunID); o.Guard.Restore(restored)` **before any
  `Authorize`** — the ordering `stats/budget/budget.go:520-528` requires. `Guard.Restore` is
  additive, so a resumed validate reports run-lifetime spend.
- **The input fingerprint** covers: the eval source content hash, `split.FingerprintSplit(seed,
  holdoutFrac)` (`adapters/evals/split/split.go:145`), the Select run ID, the agent ref, and
  `trials`. Any change refuses the resume rather than mixing populations — the rule
  `core/value_loop.go:405-408` already states.
- **Orphan spend.** Budget refusals mid-run route through `Store.RecordOrphanSpend`
  (`store/store.go:226`) as they do in Value, so `SettledSpend` stays complete across a kill.
- **Spend reporting.** `ValidateResult.Spent budget.Spend` from `o.Guard.Spent()` at close, and
  rendered through the shared surface that
  [`2026-08-31-stage-spend-reporting.md`](2026-08-31-stage-spend-reporting.md) defines. That
  plan is sequenced first; validate consumes its renderer rather than adding a fourth private
  one.

Judged goals do not enter the estimate: `goal/` contains only `exactmatch/`, and `judge/`
contains only `doc.go`. When `judge calibrate` lands (also v0.2), judge calls join the estimate
on the same ladder.

### 5 — Applying a Portfolio as a set

`ContextInjector.WithContext` takes one Asset and every implementation refuses a second
(`adapters/agent/openaicompat/context.go:64-71`). **Decision: a new Ring-0 capability, not a
loop over the existing one.**

```go
// core/ring0.go
type ContextSetInjector interface {
    // WithContextSet returns an Agent carrying every Asset, in the given order.
    // The receiver is unmodified and remains the control arm.
    WithContextSet(assets []*Asset) (Agent, error)
}
```

- Declared through `Capable` by a new `Capabilities.context_set_inject` — **`common.proto` field
  7**, additive (fields 1-6 used, `extensions` is 5; verified). Checked before scheduling, like
  every other capability (`core/value.go:161`, `core/value_loop.go:525`), so an adapter that
  cannot do it fails with `errs.ErrCapabilityUnsupported` and a `kno doctor` pointer **before any
  spend**.
- **Order is part of the measurement and is recorded.** Portfolio order is
  `PortfolioEntry.rank` (`portfolio.proto:22`, greedy on delta-per-cost), and validate applies
  that order. Prefix caching is why: `openaicompat`'s injection doc
  (`adapters/agent/openaicompat/context.go:37-43`) explains that `[system][asset]` is
  byte-identical across an Asset's sample so the provider serves it from cache; a stable
  portfolio prefix across all holdout Cases preserves that property for the whole set, which is
  the difference between paying for the portfolio's tokens once and paying `n_holdout` times.
- Ring-1 implementations for `openaicompat`, `anthropic`, `bedrock`, `vertex`, `fake` are one
  method each, joining the assets into the single system message the existing `injected.asset`
  field already holds. Each is an independent workstream per CLAUDE.md's parallelization table.
- **Rejected: loop `WithContext` N times.** It does not work — the second call returns
  `ErrInvalidInput` by design, and the design is right: that refusal exists so a per-Asset
  Valuation cannot silently become a two-Asset one. Loosening it to serve validate would remove
  a guard from the stage that needs it most.

### 6 — Which entries are applied

**Decision: v0.2 validates a Portfolio whose selected entries are ALL
`DESTINATION_CONTEXT`. A mixed Portfolio is refused unless `--context-only` is passed, and with
that flag the report labels the number as covering a subset and names the excluded entries.**

`knowledge_base` needs the writable-KB adapters that are v0.2's *other* half and do not exist
yet; `tuning_set` needs the `--bridge` Tuner path. Validating the context subset and calling the
result "the Portfolio's holdout gain" would be a number about a different set than the one the
user is about to export — the precise dishonesty prime directive 5 exists to stop. Refusing by
default, with an explicit opt-in that changes the label, is the version of this that cannot be
misread.

### 7 — Interaction effects: what ships and what does not

`report.proto:89-98` reserves `interaction_penalty_detected` and `suspect_interactions`.
**Decision: v0.2 sets `interaction_penalty_detected = false` unconditionally and emits no
suspect pairs, and the report says why in one sentence.**

The tempting rule — "flag an interaction when `holdout_gain < dev_estimated_gain`" — is
statistically illiterate and would fire on almost every honest run. `dev_estimated_gain` is
winner's-curse inflated *by construction* (`portfolio.proto:86-95`;
`docs/what-the-numbers-mean.md:17-27`), so `holdout_gain < dev_estimated_gain` is the **expected**
outcome of a correct pipeline. A detector whose positive rate is ~100% under the null is not a
detector.

The honest detector is leave-one-out on the holdout: `k+1` arms for a `k`-asset portfolio,
i.e. `(k+1) x n_holdout x trials` calls. For a 12-asset portfolio on a 40-Case holdout that is
520 calls against this plan's 80 — a 6.5x cost increase for a secondary signal. It is deferred
with a ledger entry whose trigger is a condition, not a date: **"when a Validate run reports a
holdout interval entirely below the dev estimate's interval low, or at 1.0, whichever is
first"** — the first half is a real signal that interactions are biting, observable from data
this plan starts collecting.

What validate DOES report about the set-vs-parts question, honestly: both numbers side by side,
plus their difference labelled `shrinkage`, plus one sentence stating that shrinkage is expected
and is not evidence of interaction. See §9.

### 8 — The number, and what it does and does not claim

- **`holdout_gain`** — mean paired difference, sign-corrected, over holdout Cases that scored in
  **both** arms. A Case that errored in either arm contributes to neither (the exclusion rule
  `docs/what-the-numbers-mean.md:61` already states for Value) and is counted in
  `n_dropped`. Ragged attrition that leaves fewer than two usable pairs produces **no number**:
  `not_measured = UNDERPOWERED`, matching the construction-time invariant debt #1 was repaid
  with (`TestValuationOmitsDeltaWithoutInterval`).
- **`holdout_interval`** — `interval.PairedTrials` at `interval.DefaultLevel` (0.95), method
  dispatched on `Goal.Domain()`. Never emitted without the gain; never the gain without it.
- **Is it unbiased?** Yes, for the estimand it names: *the effect of this particular Portfolio on
  the holdout population*. Nothing optimized against these Cases, so the selection effect that
  inflates `dev_estimated_gain` is absent. It is **not** unbiased for "the effect of the best
  achievable portfolio" and it is **not** a bias-corrected version of `dev_estimated_gain` —
  it is a different measurement of a different slice. That distinction goes in
  `docs/what-the-numbers-mean.md` verbatim.
- **Multiple testing: `stats/portfolio.Correct` is NOT applied, deliberately.** `Correct`
  (`stats/portfolio/portfolio.go:146`) is Bonferroni over `n_screened` — the number of Assets a
  *selection* considered. Validate screens nothing; it makes one pre-registered comparison. A
  Bonferroni factor here would widen the one interval in the product that has earned its
  nominal coverage. The plan states this in the godoc so a future reader does not "fix" it. The
  multiplicity that *does* apply is repeated holdout use across portfolios (§3), and that is
  counted and disclosed rather than corrected.
- **Relation to `dev_estimated_gain`.** Reported together, with three named contributors to the
  gap and no claim about their relative size: (a) winner's-curse shrinkage; (b) sampling noise
  on both slices; (c) **estimand mismatch** — `dev_estimated_gain` is a dev-population figure
  built from per-entry deltas scaled by `PortfolioEntry.n_routed_scale` under the uniform-effect
  model debt #65 names (`portfolio.proto:24-33`), while `holdout_gain` is a direct, unscaled
  measurement over every holdout Case. They are not the same quantity measured twice. This is
  the single most likely misreading of the whole feature and the report says it in line.
- **Underpowered holdout.** `split.Counts.Underpowered()` is `Holdout > 0 && Holdout < 20`
  (`adapters/evals/split/split.go:100`). The run executes — consistent with `MinHoldout`'s own
  godoc and with `docs/what-the-numbers-mean.md:53-59` — and the verdict, the report line and
  `--json` all carry `holdout_underpowered: true`.

### 9 — The verdict and the exit code

`errs.ExitValidationFailed = 3` already exists with the godoc *"the portfolio did not hold up
against the holdout. This is the code a deploy gate should block on."* (`core/errs/errs.go:27`).
It has never been returned. **Decision, keyed on the interval and never on the sign** — the rule
`docs/what-the-numbers-mean.md:51` already states for every other number:

| Condition on the two-sided 95% interval | Verdict | Exit |
|---|---|---|
| `low > 0` | `confirmed` | 0 |
| `low <= 0 <= high` | `inconclusive` | 0, or **3** with `--require-gain` |
| `high <= 0` | `not_confirmed` | **3** |
| no interval (underpowered / ragged) | `unmeasured` | 0, or **3** with `--require-gain` |

An interval crossing zero means "not enough evidence at this sample size", not "it failed"
(`docs/what-the-numbers-mean.md:49`), so it must not block a deploy by default — a 20-Case
holdout would then block every deploy forever and train people to pass `--force`. A gate that
wants proof-of-gain asks for it with `--require-gain`. `high <= 0` is a demonstrated
non-improvement and blocks unconditionally.

### 10 — Persistence and schema

**A new message and a new table, not a partial `Report`.**

```proto
message Validation {

  string select_run_id = 2;             // the Portfolio validated
  string value_run_id = 3;              // Portfolio.source_run_id, carried

  optional double treatment_score = 10; // mean, treatment arm
  optional double holdout_gain = 11;    // treatment − control, sign-corrected
```

## Acceptance criteria

1. `core.Validate` accepts `ValidateOptions{Evals Evals, ...}` — a plain `Evals`. A test asserts
   `core` exports no function or field whose type is `*holdoutEvals`, **and** — the check that
   closes the interface-forwarding hole *(F3)* — that `core` exports no function result, method
   result, struct field, event field or callback parameter whose type is the `Evals` interface,
   so no holdoutEvals-backed value can be handed outward under an interface. `cli` compiles
   without any reference to a holdout reader.
2. `TestOnlyValidateOpensTheHoldout` counts **`ast.CallExpr` calls to `openHoldout`** in `core`'s
   non-test files and asserts `core/holdout.go` has zero, `core/validate.go` has exactly one, and
   every other file has zero *(F1)*. Falsified three ways in a scratch commit, each of which must
   turn the test red: adding a second call in another `core` file; deleting the call in
   `core/validate.go`; and replacing the call-expression walk with a bare identifier walk, which
   must fail on the **unmodified** tree, because the declaration in `core/holdout.go` is itself an
   identifier occurrence.
3. `openHoldout` handed a `*core.SealedEvals` returns an error satisfying
   `errors.Is(err, errs.ErrHoldoutSealed)` and yields **no** iterator — not an empty one.
4. `holdoutEvals.Cases` yields exactly the `SPLIT_HOLDOUT` Cases of a mixed source, in source
   order, and yields **zero** Cases for a source of only `SPLIT_DEV` and `SPLIT_UNSPECIFIED`.
   The mirror of `TestUnassignedSplitIsNotTreatedAsDev` asserts an unassigned Case is not
   yielded as holdout.
5. `core.Baseline`, `core.Value`, `core.Select` and `core.Export` still cannot reach a holdout
   Case: the existing canaries are unmodified and still pass, and a new canary plants a holdout
   Case carrying a sentinel string and asserts the sentinel appears in no Baseline or Value row,
   event, or output.
6. `kno validate` against a Portfolio and evals whose `(eval_fingerprint, select_run_id)` already
   has a COMPLETED `holdout_uses` row exits 1 with `errs.ErrInvalidInput`, names the prior
   validate run ID, and its fix line contains `kno report --validate-run-id`. **No agent call is
   made** — asserted by a fake agent that fails the test on `Invoke`.
7. A validate killed mid-run leaves a `holdout_uses` row. **The test drives two kills, and the
   first is the one that proves the rule** *(F5)*: a kill **before the first Case is measured** —
   after the Run and the `holdout_uses` row are committed, before any `Invoke` — must still leave
   the row, because the row is written before the first agent call and not on first measurement.
   Recording-at-completion, or recording-on-first-measurement, passes a mid-run test and fails
   this one, which is why both are driven. In each case a *fresh* `kno validate` for that pair is
   then refused with a fix naming `--resume`; `kno validate --resume --run-id <id>` completes, and
   `Store.SettledSpend` for that run equals first-process + second-process spend with no Case paid
   for twice. The completed run's `Validation.measured_case_count` equals the holdout size.
8. Validating a second, different Select run against the same eval fingerprint without
   `--allow-repeat-holdout` is refused; with it, the run completes, `holdout_use_index == 2`,
   `--json` reports `holdout_uses: 2`, and the human report contains the string
   `this holdout has measured 2 portfolios`.
9. The consent quote for `n_holdout = 20, trials = 1` states **40** calls and shows the
   `20 x 2 arms x 1 trial` derivation. A test asserts the quoted call count is exactly
   `2 * holdout * trials` for a table of `(holdout, trials)` pairs.
10. `kno validate` with `--yes` and a cost cap that admits fewer than `2 * n_holdout` calls stops
    at the cap, exits `errs.ExitBudgetStopped` (2), records `RUN_STATUS_BUDGET_STOPPED`, emits no
    `holdout_gain`, and is resumable.
11. `ValidateResult.Spent` equals `Guard.Spent()` at close, and equals `Store.SettledSpend` for

12. `holdout_gain` is present **iff** `holdout_interval` is present. A test drives a holdout of

13. `holdout_gain` for a synthetic agent whose treatment arm scores exactly `+0.1` on every

## Alternatives considered

**A capability token instead of an unexported type.** `Seal` returns a value; a symmetric
`Unseal(token ValidateToken)` was the obvious mirror. Rejected: any token minted inside `core` is
forgeable by anything inside `core`, so the token buys nothing the unexported type does not,
while costing an exported type, an exported constructor, and a public API surface that promises
a guarantee it cannot keep. Worse, an exported token invites `cli` to hold one — and the moment
a holdout iterator can exist outside `core`, the guarantee degrades from "impossible" to
"reviewed".

**A second seal type exported from `core`: `core.HoldoutEvals` + `core.OpenHoldout`.** Rejected
for the same reason at lower cost: it is *usable* by `cli`, `api` and any future consumer, and
prime directive 5's guarantee should not depend on those callers being careful. The unexported
form gives up nothing — `ValidateOptions` takes the raw `Evals` either way.

**Cache the control arm per eval fingerprint and replay it for later portfolios.** *(F4)* The
control arm does not depend on the Portfolio, so recording it once per
`(eval_fingerprint, agent_ref, resolved_model, trials)` would halve the marginal cost of every
`--allow-repeat-holdout` validation after the first — 40 → 20 calls at `MinHoldout`, 480 → 240
at a 400-Case, 3-trial routed scale — with no dev/holdout confound, because a cached control is
still a holdout measurement. **Deferred, not rejected** (§1): a replayed arm breaks within-run
pairing and reintroduces exactly the provider-drift gap this plan uses to reject
`kno baseline --holdout`; it pays only on the path §3 discourages; and its invalidation rule fails
toward a wrong headline number rather than a crash. Ledgered with a trigger.

**Compare the holdout treatment score against the recorded dev baseline mean.** Halves the cost.
Rejected on identifiability: the estimand becomes portfolio effect confounded with a random
dev/holdout population difference (§1), and at `MinHoldout = 20` the confound can dominate.
Cheap and wrong.

**Reuse `knov1.Report` as validate's persisted output.** Rejected: `Report` carries portfolio,
gaps, agent, goal, total cost and case counts that validate does not compute, so validate would
either fabricate them or write a `Report` that is mostly absent — and `Report`'s `optional`
fields exist precisely so absence means "not run", which a half-written Report would corrupt.

**Refuse a second portfolio against the same holdout, unconditionally.** Statistically the
purest answer. Rejected: the user's next move is `rm kno.db` or `--split-seed`, converting a
counted peek into an invisible one, and the tool would have traded an honest number for a
comfortable rule. §3.

**Detect interactions from `holdout_gain < dev_estimated_gain`.** Rejected: fires under the null
at ~100% because dev inflation is the expected state (§7).

**Loop `WithContext` over the Portfolio's Assets.** Rejected: every adapter refuses the second
call by design, and that refusal protects the Value stage (§5).

## Edge cases

| Case | Behavior |
|---|---|
| Holdout below `split.MinHoldout` (20) | Runs. `holdout_underpowered: true`, caveat attached to the number, verdict per §9, exit unchanged |
| Holdout of exactly 0 | Refused before spend, `ErrInvalidInput`. `split.Counts.Validate` refuses this at Baseline, but the eval source can change between runs, so it is re-checked |
| Holdout of 1 usable pair | No interval, no gain, `not_measured = UNDERPOWERED`, verdict `unmeasured`, exit 0 |
| Holdout smaller than the entries' dev routed slices | **Not an error.** Routing is a dev-side concept; the Portfolio applies to every holdout Case. The report states the estimand mismatch (§8c) rather than refusing |
| Portfolio selects nothing | Exit 0, no agent call, no `holdout_uses` row, "nothing to validate" |
| An Asset in the Portfolio is missing from the Pool | Refused before spend, every missing ID named |
| An Asset's content changed since Select | Refused before spend via `PortfolioEntry.content_hash`, Asset named |
| Portfolio has mixed Destinations | Refused unless `--context-only`; with it, subset-labelled and excluded IDs listed |
| Select run was `BUDGET_STOPPED` / has `source_incomplete_reason` | Runs. The reason is copied into `Validation.incomplete_reason` and printed; Select already made the partiality decision |
| `--select-run-id` names a non-Select run, or the chain to Value/Baseline is broken | Refused before spend, `ErrInvalidInput`, mirroring `cli/report.go:270-294` |
| Evals changed since Select (fingerprint mismatch) | Refused. Re-splitting would reclassify Cases and a "holdout" containing formerly-dev Cases is not a holdout |
| Second validate, same portfolio, prior run COMPLETED | Refused, no flag, pointer to the recorded result |
| Second validate, same portfolio, prior run INTERRUPTED | Fresh run refused; `--resume` continues the same run |
| Second validate, different portfolio, same evals | Requires `--allow-repeat-holdout`; use index recorded and printed |
| Interrupted mid-run (SIGINT / deadline) | `RUN_STATUS_INTERRUPTED`, exit `ExitInterrupted` (4), no verdict, `holdout_uses` row already written, resumable |
| Budget cap hit mid-run | `RUN_STATUS_BUDGET_STOPPED`, exit 2, no gain emitted, resumable |
| Agent lacks `context_set_inject` | `ErrCapabilityUnsupported` before spend, `kno doctor` pointer |

  *Removing the seal from any pre-Validate stage fails at least four of these.*
- **One-shot.** `TestValidateRefusesASecondRunOnTheSamePortfolio`;
  `TestInterruptedValidateStillConsumesTheHoldout`, driven **twice** — killed before the first
  Case and killed mid-run *(F5)*; `TestResumeContinuesRatherThanRepeating`;
  `TestRepeatHoldoutUseIsCountedAndDisclosed`. *Making consumption recorded-at-completion, or

  variant alone would not catch.*
- **Money.** `TestQuoteCountsBothArms` (table over `(holdout, trials)`);
  `TestValidateResumeDoesNotDoubleSpend` (kill mid-run, resume, assert `SettledSpend` and

## Rollback

Deleting `core/validate.go`, `core/holdout.go`, `cli/validate.go` and reverting the four
`cli/report*` hunks restores v0.1 behavior exactly: the caveat becomes unconditional again and
`validated_on_holdout` returns to a hardcoded `false`. The proto additions are additive and
unreferenced by pre-existing code, so they can stay. The two store tables are additive and
never read by v0.1 code paths; the migration is not reversed (SQLite migrations in this repo are
forward-only) and the tables are simply orphaned. `PortfolioEntry.content_hash` written by an
un-rolled-back Select is ignored by everything. `docs/status.json` is regenerated by
`make status`.

The one irreversible thing is intentional: `holdout_uses` rows already written record that a
holdout was peeked at. Rolling back the code does not un-peek it, and deleting those rows would
be the tool lying about its own history.

## Accepted risks

Each of these gets a `docs/debt.md` row with a repayment trigger that cannot self-satisfy.

- **Repeated holdout use is counted, not corrected.** Validating N portfolios against one
  holdout re-introduces multiplicity at rate N; the interval is not widened. *Trigger: when a
  `holdout_uses` count reaches 3 for any eval fingerprint in a real run, or before 1.0.*
- **Pairwise interaction detection is not shipped**, against `DESIGN.md:88`. §7 gives the cost
  and the reason. *Trigger: when a Validate run reports a holdout interval entirely below the
  dev estimate's interval low, or 1.0, whichever is first.*
- **The number is a context-injection upper bound**, inheriting
  `docs/what-the-numbers-mean.md:106` wholesale. Knowledge- and tuning-destination entries are
  refused rather than approximated. *Trigger: the first writable-KB adapter (v0.2's other half).*
- **`--context-only` produces a number about a subset.** It is labelled everywhere it appears,
  but a labelled subset number is still a number someone can quote out of context. *Trigger:
  when both other Destinations are validatable.*
- **The dev/holdout comparison is between two estimands, not two measurements of one.** §8c. It
  is stated in the report and the docs rather than resolved, because resolving it means measuring
  the portfolio on the dev slice unscaled — another full arm's spend. *Trigger: when debt #65's
  uniform-effect scaling model is replaced.*
- **The dark-spend window (`docs/debt.md#20`) applies here too.** A SIGKILL between a provider
  accepting a request and the row being persisted is unobservable, so a resumed validate can
  under-count spend by up to `concurrency` calls. Inherited, not introduced.
- **`knov1.Report` still has no producer.** This plan adds `Validation` and does not fix that.
  *Trigger: the v0.3 `serve` PR, which needs a Report on the wire.*
- **The control arm is re-measured for every validation, at 2× the naive call count** *(F4)*.
  The cached-control design in §1 would halve the marginal cost of the second and later
  validation of one holdout; it is deferred because a replayed control breaks within-run pairing
  and its invalidation rule fails toward a wrong number rather than a crash. *Trigger: when a
  `holdout_uses` count reaches 3 for any eval fingerprint in a real run — the same signal that
  triggers the multiplicity row — or the first issue reporting a validate quote declined on cost.*
- **`TestOnlyValidateOpensTheHoldout` is a bespoke AST test, not a toolchain assertion** *(F2)*.
  It reasons about call expressions inside one package and can in principle be evaded by an alias
  or a wrapper the walk does not model. It is the only mechanism available for an in-package
  boundary, and its own correctness is pinned by criterion 2's three falsifications rather than by
  precedent. *Trigger: any PR that adds an indirection through which `openHoldout` could be
  reached, or 1.0.*
- **The holdout split is recomputed, not persisted.** Stability rests on `AssignSplit`'s
  determinism plus the fingerprint check. A change to `splitResolution` or the hash function
  would silently redefine every holdout. *Trigger: any PR touching
  `adapters/evals/split/split.go`'s hashing.*
