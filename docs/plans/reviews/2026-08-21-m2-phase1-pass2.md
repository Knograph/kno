# Phase-1 Second-Pass Adversarial Review — M2 plan (amended)

**Verdict up front: BLOCK.** The amendment fixes many real defects, but its largest new section (§2.3) is built on an arithmetic claim that is false against `stats/budget/budget.go` as it exists on `main`, and the design erected on top of that claim introduces a feedback loop, a resume dead-end, a core/adapters ownership hole, and a public Go API change — all to solve a problem the guard does not have. Separately, moving `kno purge` to M2-3 while pulling debt 27 into M2-6 created a direct collision between two PRs in the same milestone.

## HIGH

### H-A. §2.3's justification for abandoning pure pessimism is arithmetically wrong. The entire adaptive design is unnecessary.

**The claim** (§2.3, "Reservation strategy (H8)"): *"output at $8/Mtok with `max_output_tokens = 4096` reserves $0.0328 per Case… A `--max-cost-usd 5.00` run authorizes ~152 Cases and stops `BUDGET_STOPPED` having actually spent ~$0.30 — 6% of the cap."*

$5.00 ÷ $0.0328 = 152. That is the arithmetic of a guard in which reservations accumulate and are never returned. This guard returns them:

- `stats/budget/budget.go:229-232` — `fitsLocked` tests `g.spent.CostUSDMicros + g.reserved.CostUSDMicros + est.CostUSDMicros > cap`.
- `budget.go:316-322` — `Settle` calls `g.releaseLocked(r.id)` **and then** adds `actual` to `spent`.
- `budget.go:350-357` — `releaseLocked` **decrements** `g.reserved`.
- `core/baseline.go:481,493` — `invokeOnce` settles (or releases) before returning, per Case, per attempt.

So `g.reserved` is only ever the *in-flight* set — at most `concurrency` reservations — and `g.spent` accumulates **actual** cost. The plan's own §2.3 states these three properties correctly two paragraphs earlier and then contradicts them.

**Actual behavior, same inputs:** cap $5.00, pessimistic $0.0328/Case, actual ~$0.002/Case, concurrency 8. The guard denies when `spent + 8×0.0328 + 0.0328 > $5.00`, i.e. at ~$4.70 of **real** spend. The run completes ~2,350 Cases and uses 94% of the cap, not 6%.

**What pure pessimism actually costs** is `N × pessimistic` of headroom held back at the boundary — 5.2% of a $5 cap at N=8 with a 4096-token ceiling. It only becomes a real failure when `N × pessimistic` is comparable to the whole cap: with a 32k reasoning ceiling ($0.256/Case) and `--max-cost-usd 1.00`, the 4th concurrent Case is denied (4 × $0.256 > $1.00), `IsFatal` fires, and the run ends `BUDGET_STOPPED` after ~3 Cases having spent ~$0.006. *That* is a genuine H8-shaped bug — but its shape is `N × pessimistic vs cap`, not `cap ÷ pessimistic`.

**Cheaper fix (the design Alternative F was rejected against a false premise):** keep pure pessimism; add a startup feasibility check. If `concurrency × pessimistic_per_case` exceeds some fraction of the cap, reduce effective concurrency to `max(1, floor(cap × f / pessimistic))` and say so in the CLI grammar, or refuse with an actionable message naming both numbers. ~20 lines in `core`/`cli`. No proto change, no `BaselineOptions` signature change (§2.11 dissolves), no running quantile, no resume state, no feedback loop, no order-dependent reservation. The honest cap bound `C + N × δ_max` survives with δ_max ≈ the BPE input under-count only — small, and genuinely bounded.

Everything in H-B, H-C and most of H-D exists only because of this.

### H-B. §2.3's "settle at the reservation" + adaptive quantile is a self-referential estimator that can drift monotonically upward.

Section 2.3 states two rules that interact:

1. Missing usage block → *"settle at the reservation (never zero)."*
2. Reservation after the first `k` Cases → *"a high quantile (p95) of observed settled cost × a safety multiplier."*

The sample feeding rule 2 therefore contains values produced by rule 1. Concrete sequence: a self-hosted OpenAI-compatible server (llama.cpp, older Ollama, some OpenRouter models) omits `usage` on 60% of responses. First `k` Cases settle pessimistically at $0.0328. p95 over that sample × multiplier 1.5 = $0.049. The next batch's missing-usage Cases settle at $0.049. p95 climbs to ~$0.049 × 1.5 = $0.074. With a majority of settlements sourced from the previous reservation, `r_{n+1} ≈ r_n × m` — geometric growth, capped only by the cost cap binding. The run stops at a small fraction of its cap for reasons no user can diagnose — reintroducing exactly the H8 failure mode the adaptation was added to fix, now unpredictably and dependent on the provider's usage-reporting rate.

The first review killed "settle at the estimate"; settling at the *reservation* is not the same bug renamed **under pessimism** (the reservation is a true ceiling, so it over-charges the budget, which is safe). It becomes a worse bug under adaptation, because the reservation is no longer a ceiling and the settled value is fed back into the thing that computes it.

**Fix shape:** if adaptation survives H-A, (a) exclude reservation-settled Cases from the quantile sample entirely, and (b) clamp every reservation at the pessimistic ceiling regardless of what the sample says. Both are one-line invariants and both must be property-tested.

### H-C. §2.3 and §2.11 describe two different estimators, and neither has a home for the adaptive state — or for resume.

- §2.3: *"the reservation is a high quantile (p95) of observed settled cost"* — one global number, refreshed as the run proceeds.
- §2.11: *"a per-Case estimate requires an injected `func(*Case) budget.Estimate` on `BaselineOptions`"* — a pure function of a Case.

A `func(*Case) budget.Estimate` is stateless and cannot observe settlements. So either the quantile lives in `core` (and `core/baseline.go` — already **657 lines** against CLAUDE.md's ~400 soft cap — grows a streaming quantile estimator), or the estimator is not a func but an interface with an `Observe(budget.Spend)` method, which is a different and larger public API change than §2.11 describes, and which `adapters` must implement while `core` drives it. The plan never says which. Prime directive 3 is not *breached* by either (`core` already imports `stats/budget`, `core/baseline.go:13`), but the ownership is undefined and two PRs (M2-2, M2-4) would each assume the other owns it.

The plan also never specifies `k`, the multiplier, or the quantile algorithm. A p95 over 20 samples is the max or second-largest — an extreme order statistic with enormous variance — and it is undefined below ~20. Under concurrency N the first N reservations are all made from an empty sample.

**Resume loses the sample, and the failure is concrete.** `store.SettledSpend` (`store/sqlite.go:313-330`) returns an aggregate `budget.Spend` — calls, cost, tokens. There is no distribution. `Guard.Restore` (`budget.go`) restores only spend. So a resumed run re-enters the pessimistic first-`k` phase with a nearly-exhausted cap:

> Cap $5.00. Killed with $4.97 settled. `--resume`: `Restore` sets `spent = $4.97`, remaining $0.03. First Case reserves pessimistically at $0.0328 → `fitsLocked` false → `ErrBudgetExceeded` → `IsFatal` → run ends `BUDGET_STOPPED` with **zero Cases done** — and `cli/render.go:184` prints *"Stopped at the budget. Run `kno baseline --resume` to continue where it left off."* The user resumes forever, paying nothing and progressing nothing.

Under uniform pessimism this cannot happen, because the run stops at the same reservation size it resumes at. Mixing two regimes across a process boundary creates it.

**Fix shape:** if adaptation survives, seed the sample on resume from `SettledSpend.CostUSDMicros / SettledSpend.Calls` (available today, no schema change) and clamp; and separately, a budget stop that completed zero Cases must be a distinct, non-resumable message.

### H-D. §2.4's run-level confirmation names a number that is undefined, ignores the cap, and cannot be computed on `--resume`.

The H4 diagnosis is correct and verified (`budget.go:271` sets `g.confirmed = true` once; `Authorize` receives one operation's estimate). The fix is under-specified in three ways, each producing a wrong number in front of a human at the consent moment:

1. **Which estimate?** §2.3 makes the per-Case number vary. If the run-level figure uses the pessimistic first-`k` value, `10,000 × $0.0328 = $328` is shown for a run that will cost ~$30. Users who learn the prompt is 10× inflated stop reading it — which disarms the confirmation exactly when a genuinely expensive run appears. If it uses the adapted value, the prompt fires before any adaptation has happened.
2. **The cap is ignored.** With `--max-cost-usd 5.00` set, the honest maximum exposure is $5.00 + `N × δ_max`, not $328. Presenting $328 when the guard will stop at $5 is simply false.
3. **Resume is unaddressed and unimplementable as designed.** §2.4 puts the computation in the CLI because *"it already has `counts.Dev`."* But `cli/baseline.go:200` passes `counts.Dev` unconditionally, and the set of already-completed Cases is loaded **inside** `core.Baseline` (`core/baseline.go`, `opts.Store.CompletedCases`). The CLI cannot compute `DevCases − done` without a second store query it does not currently make. So a run killed at 9,988/10,000 prompts the user to approve **$328** for 12 remaining Cases.

**Fix shape:** state the number as a bounded range capped by the cap — *"at most $X (your cap), typically ~$Y"* — and move the run-level confirmation into `core.Baseline` after `CompletedCases` is loaded, where the remaining count is known. That also keeps `cli`/`api`/`tui` as shells over one engine call rather than three reimplementations of the estimate.

### H-E. M2-3 (`kno purge`) and M2-6 (debt 27) collide: purge destroys the data M2-6's repayment reads.

`store/sqlite.go:38-48` — the `outcomes` table stores the Score only as `score_proto BLOB`. There is no numeric score column; `scored` is a 0/1 flag used by `OutcomeCounts` (`sqlite.go:296-311`).

- **`docs/debt.md#25`** says trace content lives in `outcomes.response_proto`/`score_proto` and *"a purge that NULLs only the blob columns is safe."* §3's M2-3 row: *"`kno purge` — nulls blobs, never deletes rows."*
- **`docs/debt.md#27`** prescribes the fix as *"summing `score_proto` values in the store alongside `OutcomeCounts`."* §3's M2-6 row and §10 claim it repaid there.

So M2-3 nulls the blob that M2-6 must sum. Concrete failure: user runs `kno baseline`, runs `kno purge` for privacy, is interrupted, runs `--resume`. `CompletedCases` and `SettledSpend` survive (both read dedicated columns — the entry-25 guarantee holds). But M2-6's aggregate now sums over the unpurged subset only, and reports it as the run's `AggregateScore` — printed at `cli/render.go:166`, emitted in `--json` at `cli/jsonreport.go:65`, **and carried on the event stream as `RunFinished.aggregate_score`** (`proto/kno/v1/event.proto`). A silently-wrong reference number, produced by two features the same milestone ships, is the exact prime-directive-5 failure debt 27 exists to close.

**Fix shape:** add a `score_value REAL` column (and `score_passed`) to `outcomes` in M2-0/M2-3; purge nulls `response_proto` and clears only `Score.rationale`/`judge_model` inside `score_proto` (or nulls it entirely, since the number now lives in a column); M2-6 sums the column. Also add the test `docs/debt.md#25` explicitly requires and §7 omits (see M-e), extended to assert the aggregate is unchanged by a purge.

### H-F. §2.5's determinism rules are provider-hostile in one direction and spend-inducing in the other.

**`temperature: 0` as a default breaks a whole model class.** OpenAI's reasoning models reject any `temperature` other than the default with a 400; Anthropic constrains `temperature` when extended thinking is on. A blanket default means `kno baseline --agent openai:<reasoning-model>` returns a 400 on every Case at concurrency N, every Case errors, `closeRun` sets `ErrorRateExceeded`, and the user is told *"too many cases errored for this to be a usable baseline"* — an error message that names nothing about the actual cause. §2.10 builds a static per-adapter capability matrix; sampling-parameter support belongs in it, and §2.5 never routes it there.

**Folding the resolved model into `checkResumable` causes false refusals that cost money.** `core/baseline.go:368` currently compares `run.GetAgent().GetRef()`; §2.5 adds the provider-reported resolved model and `system_fingerprint`. Two problems:

1. `system_fingerprint` changes whenever the provider's backend config changes — routinely, within hours, with no model change. An equality check turns that into `ErrCheckpointStale`, whose fix line (`core/errs/errs.go:75`) is *"re-run without --resume to start a fresh run"* — i.e. pay for the entire run again. A false refusal that costs the full run price is worse than the blending it prevents.
2. §2.5 says capture *"from the first response."* With concurrency N there is no "first response" — it is whichever of N in-flight calls returns first. During a provider rollout, two workers in the *same* run legitimately receive different fingerprints, so the recorded value is a random sample of a mixture the check cannot detect anyway.

**Fix shape:** compare `response.model` (the resolved alias) as a **hard** refusal — that is the case `checkResumable` was written for. Treat `system_fingerprint` as **recorded and warned**, never refused, and say so in `docs/what-the-numbers-mean.md`. Record the *set* of fingerprints observed, not the first, so a mixture is visible rather than sampled.

### H-G. §2.1's "the transport does not retry" is not achievable as stated, and refusing all transport retries has no landing place in `core`.

The §2.1 *diagnosis* is right: `core/baseline.go:644` settles every Response as `Calls: 1`, so a retrying transport makes N provider calls inside one reservation. The *remedy* — "the transport does not retry" — is asserted as though it followed from not writing retry code. It does not:

- `net/http`'s `persistConn.shouldRetryRequest` replays a request on a reused connection when nothing was written, provided `req.GetBody != nil` — which `http.NewRequest` sets automatically for a `*bytes.Reader`/`*bytes.Buffer` body. That case is benign for money (the provider never saw it) but means "does not retry" is false and untested.
- **The dangerous interaction is with §11.2 / `docs/debt.md#20`.** `isReplayable()` returns true for a POST that carries an `Idempotency-Key` header. The moment the adapter sets one to close part of the dark-spend window — the exact investigation §10 assigns to entry 20 — the stdlib begins transparently replaying that POST on `errServerClosedIdle` and `transportReadFromServerError`, the latter being a case where bytes *were* written and the provider may have processed them. So the milestone's own remedy for entry 20 switches on the retry behavior §2.1 forbids, silently, with no code change visible in review.

**And the converse half:** `core` retries **only** `ErrRateLimited` (`core/baseline.go`: `if !errors.Is(err, errs.ErrRateLimited) … return nil, err`). There is no transient-transport sentinel in `core/errs/errs.go` (the set is Budget/HoldoutSealed/Capability/CheckpointStale/InvalidInput/Interrupted/RateLimited). So a stale pooled connection becomes a terminally errored Case, `codeOf` labels it `AGENT_ERROR`, and at concurrency 8 against a provider with a 60s idle timeout, any pause in a long run errors a handful of Cases — 5% of which trips `DefaultMaxErrorRate` and marks a good baseline unusable.

**Fix shape:** (a) explicitly `req.GetBody = nil` after construction, or wrap the `RoundTripper` in a counter and assert exactly one round trip per reservation in the misbehaving-server suite; (b) add an `errs.ErrTransportTransient` sentinel and let `core.invokeWithRetry` retry it under the same reservation-per-attempt discipline; (c) add an explicit test with a server that closes idle connections, asserting the count of requests **observed at the server**, not at the client.

### H-H. §2.8 has no key-resolution design for the `@base-url` form — which is the entire point of §2.2.

§2.8 binds *"each key env var … to a default-host allowlist"* and says sending a key to a non-default host *"requires an explicit opt-in flag."* But §2.2's headline example is `openai:llama-3.3-70b@https://api.groq.com/openai/v1`, and Groq needs `GROQ_API_KEY`, not `OPENAI_API_KEY`. The plan never says how a credential is selected for an arbitrary base URL. The three possibilities:

- reuse `OPENAI_API_KEY` behind the opt-in flag → the documented cookbook recipe (§9: *"a new recipe for pointing Kno at your own provider"*) ships the user's OpenAI key to a third party, which is threat #1 of §2.8 reached by following the docs;
- a `--api-key-env` flag → keys named on the command line is fine, but nothing in §2.8 describes it;
- a per-host key map → needs a config surface, and §2.8 forbids `kno.yaml` for keys.

The primary use case of the milestone's headline feature has no credential model.

**Fix shape:** per-host key resolution (`KNO_API_KEY_<NORMALIZED_HOST>`, falling back to the scheme default only for the scheme's default host), and make the opt-in flag mean *"use key K for host H"* rather than *"send whatever key you have to wherever."* A key bound to host A must never reach host B, flag or no flag.

### H-I. §10 re-dates `docs/debt.md#29` to "M4," which is not a defined milestone — and the plan's own §5 argument says to repay it in M2-0.

**"M4" does not exist.** DESIGN.md's Milestones section (lines 395-402) defines **v0.1, v0.2, v0.3, v0.4** — there is no M1–M4 anywhere in it. The only occurrence of "M4" in the repository outside this plan is `docs/plans/2026-08-19-m1-baseline.md:218`, where it refers to when the **Validate** stage is due, not the TUI. So §0's *"M4 is a named milestone, not 'whenever'"* is false as written: it is a token used once, for a different thing, with no plan, no scope, and no date. `CLAUDE.md`'s ledger rule — *"'Someday' is not a trigger; an entry without one is a rejected review finding, not accepted debt"* — is not satisfied by a milestone that exists only as prose in another plan. This is the same failure §0 correctly accuses the first draft of.

**And it is unnecessary.** `docs/debt.md#29`'s prescribed fix is *"Either add a `RunResumed` payload or have the resumed `RunStarted` carry the remaining count"* — a purely additive `event.proto` change. §3's M2-0 row already opens `event.proto` for three new payloads and already takes a `buf breaking` review. That is verbatim the argument §5 makes for repaying entry 26 in M2-0 rather than re-dating it (*"§5 already opens the `Run` message… re-dating buys a second `Run`-touching proto churn plus another `buf breaking` review"*). The plan applies its own reasoning to 26 and declines to apply it to 29. Note also that `core/baseline.go` calls `opts.emitRunStarted(ctx, agg, opts.DevCases)` unconditionally — the full count on resume — so the emitter-side fix is a two-line change in the same milestone.

**Fix shape:** repay 29 in M2-0 (payload) + wherever the resume path is touched (emitter). If it genuinely must be deferred, the trigger must be a condition or a date, not an undefined token.

## MEDIUM

**M-a. `Outcome.Spend` under-records retried calls, and §2.6 widens the gap.** `store/store.go:124` documents `Spend` as *"including any failed attempts preceding a successful retry. One Case yields one outcome but may incur several charges."* The code does not do this: `core/baseline.go:518,528` set `out.Spend = spendOf(r.Value.Response)`, which is always `Calls: 1` (`baseline.go:644`). The guard settles each attempt separately (`baseline.go:486,493`), so a Case that took 3 attempts settles 3 calls in memory and persists 1. `Guard.Restore(SettledSpend)` on resume therefore under-restores the call cap by (attempts − 1) per retried Case. Today the fake rarely retries; M2 makes 429s routine, and §2.6 replaces a 3-attempt bound with a **time** bound, multiplying the divergence. *Fix:* accumulate per-attempt spend in `invokeWithRetry` and carry it on `caseOutcome`; add a resume test that kills a run mid-retry and asserts `SettledSpend.Calls` equals `Guard.Spent().Calls`.
