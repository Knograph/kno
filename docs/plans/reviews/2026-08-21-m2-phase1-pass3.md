# Phase-1 adversarial review, pass three — `docs/plans/2026-08-21-m2-first-provider-adapter.md`

## What I verified independently first

**The §2.3 measurement is directionally right and numerically wrong.** I built a simulation against the real `stats/budget` (N goroutines: `Authorize(pessimistic)` → hold → `Settle(actual)`, denial fatal), cap $5.00, pess $0.0328, actual $0.002:

```
zero-latency (no in-flight overlap):
  conc=1  completed=2484  $4.9680  99.36%
  conc=8  completed=2454  $4.9080  98.16%   <- reproduces the plan's "2455 / $4.91 / 98.2%"
with a real in-flight hold (what a provider call does):
  conc=1  completed=2484  $4.9680  99.36%
  conc=8  completed=2378  $4.7560  95.12%
  conc=32 completed=2007  $4.0140  80.28%
```

So: **pass one's H8 (~6%) was indeed wrong and the plan is right to delete the adaptive estimator.** But the quoted 98.2% is an artifact of a simulation where the reservation is released in the same instant it is taken — under genuine concurrency-8 overlap it is 95.1%, and the forfeiture scales as `N × pess / cap` (conc 32 → 80%). §2.3 also contradicts itself: the prose says the guard "denies at `spent + N×pessimistic + pessimistic > cap` — i.e. at ~94%", the table says 98.2%. Both are wrong; the correct condition is `spent + (N−1)×pess + pess > cap`, i.e. `spent + N×pess > cap`, and the true answer (≈95% at N=8) sits between the two numbers the same section prints two paragraphs apart. This is the third arithmetic claim in this lineage that does not survive measurement.

## HIGH

### H-1. §2.3's reservation is per-Case; §2.11's deletion left no mechanism to compute one. The two sections cannot both ship.

§2.3: *"Reservation = pessimistic, always. `input_tokens × input_price + max_output_tokens × output_price`, counted locally."* `input_tokens` is a property of **the Case**.

§2.11: *"The flat `EstCostPerCallUSDMicros` is replaced by an adapter-supplied pessimistic prediction computed at the adapter, and `core` keeps the scalar shape it already has. No `core` API break."*

Against the code:
- `core/ring0.go:18-25` — `Agent` is `Invoke(ctx, *Case) (*Response, error)`. Nothing else.
- `core/baseline.go:397` — `est := budget.Estimate{Calls: 1, CostUSDMicros: o.EstCostPerCallUSDMicros}` is built **before** `Invoke`, from a run-scalar.

There is no path by which an adapter supplies a per-Case number to `core` before the call, without either (a) the injected `func(*Case) budget.Estimate` §2.11 just deleted, or (b) a new optional Ring-0 interface (`Predictor`/`Predict(ctx, *Case) (budget.Estimate, error)`) that `core` type-asserts. (b) is a `core` public-API addition — it is in no PR row, not in §5, and explicitly denied in §2.3 ("no public `core` API change") and §8 ("§2.3's simplification removed the API change entirely").

If the scalar is genuinely kept, then the reservation does not depend on the Case's input tokens, which means it is not pessimistic for long Cases and is the flat hand-supplied guess §1 item 3 says the milestone exists to replace.

This is the same failure class as draft 2: the largest section rests on something that is false against the code. **Fix shape:** admit the Ring-0 addition. Add `core.Predictor` as an optional interface alongside `Capable`/`ContextInjector` (adapters that don't implement it fall back to `EstCostPerCallUSDMicros`), list it in §5's impact, list it in §8 as not-rolling-back-cleanly, and give it a PR row before M2-5.

### H-2. "Settle at the reservation when usage is missing" breaks the single-derivation invariant in `core/baseline.go`, and the divergence lands in `Guard.Restore`.

`core/baseline.go:490-493`:
```go
// The same computation the sink persists. Two independent derivations of
// one Case's cost could drift, and the persisted one is what
// Guard.Restore reads on resume.
res.Settle(spendOf(resp))
```
`spendOf` (`:644-650`) reads `r.GetCostUsdMicros()`. The sink persists the same call at `:518` and `:528`.

§2.3 says a Response with no usage block settles **at the reservation**. But the reservation is held by `core` (`res`), not visible to `spendOf`, and the sink has no `res` at all. Implemented literally: guard charges `res.Estimate().CostUSDMicros`, store persists `spendOf(resp)` = 0. Kill the run, `--resume`, `SettledSpend` under-restores by the full inferred cost of every usage-less Case, and the resumed run spends its cap a second time — precisely the amnesia the M1-0 comment at `:521-525` closes.

**Fix shape:** the adapter, which computed the prediction, stamps it onto `Response.cost_usd_micros` and sets `usage_estimated=true`. `spendOf` stays the single derivation and both sides agree. Say this explicitly; the plan currently implies core does it.

### H-3. `score_value` has no migration story, and `CREATE TABLE IF NOT EXISTS` makes the first paid run against an existing `kno.db` fail after the money is spent.

`store/sqlite.go:19-20`: *"It is idempotent, so opening an existing database is a **no-op rather than a migration**."* `:38-49` is `CREATE TABLE IF NOT EXISTS outcomes (…)`; `:129` applies it on every open.

Sequence: user ran M1 with the default `--db kno.db` (`cli/baseline.go:75`). M2-1 merges, adding `score_value`/`score_passed` to the DDL string. User upgrades and runs `kno baseline --agent openai:…`. `NewSQLite` succeeds (table exists, statement skipped). First Case: provider call made, money spent. `RecordOutcome`'s INSERT (`:253-259`) now names `score_value` → `table outcomes has no column named score_value` → sink error → run aborts. Every retry repeats it. Paid calls, zero rows recorded, zero resumability. §2.9a never mentions migration.

Second half, worse: even **with** an `ALTER TABLE ADD COLUMN`, M2-8's `SUM(score_value)` over rows written before the column existed sums NULL/0 while `OutcomeCounts` still counts those Cases in `priorScored` (`core/baseline_events.go:52,84-89`). The resumed `AggregateScore` is then not merely partial — it is **numerically wrong and biased toward zero**, printed at `cli/render.go:166`, put in `--json` at `cli/jsonreport.go:65`, and carried as `RunFinished.aggregate_score`. That is strictly worse than debt 27, which at least is documented as partial. And a run purged *before* the upgrade has no `score_proto` to backfill from, so it is unrecoverable forever.

**Fix shape:** `PRAGMA user_version` + a real migration path in M2-1 with a test that opens an M1-era database; backfill `score_value` from `score_proto` where present; for rows where it is absent (purged, or purged-then-upgraded), mark the run and **refuse to report an aggregate** rather than report a wrong one — prime directive 5.

### H-4. The settlement-time ceiling cannot enforce anything, so §11.1's "narrowed, not accepted" is false — and it is the only accepted risk with no ledger row.

`budget.go:229-241` (`fitsLocked`) already denies every subsequent `Authorize` the moment `spent ≥ cap`, for any positive estimate. So once settlement overshoots, enforcement is already total. A check inside `Settle` can add exactly one thing: **observability** (recording `spent − cap`, which `remainingLocked`'s `max(0, …)` at `:375` currently hides). That is worth doing. It is not enforcement.

Consequence: §11 item 1 says the soft-cap risk is *"narrowed, not accepted"* and therefore carries no §10 row. Every other §11 item has one. If the narrowing claim is false, §11.1 is an accepted risk with no trigger and no owner — the exact ledger-rule violation the plan's §0 accuses draft 1 and draft 2 of.

And on the mechanics, per your question: if `Settle` gains an error return, `core/baseline.go:486` and `:493` ignore it → `errcheck` fails (zero tolerance). If core honors it, a Case that made a successful, paid, scored call becomes an errored Case — losing paid work and inflating `ErrorRateExceeded`. If `Settle` clamps `spent` to the cap, `Guard.Spent()` (`:416-420`) — *"This is the number a report shows"* — under-reports the real invoice, and `--json`'s `spent_usd` lies to a CI gate. `Restore` (`:402-409`) is additive with no check at all and runs at `core/baseline.go:212`, so a resume with a lowered `--max-cost-usd` enters over-cap without ever touching `Settle`.

**Fix shape:** keep `Settle` void. Add `Guard.Overshoot() int64` plus the overshoot event; state in §11.1 that the bound remains `C + N × δ_max`, **accepted**, now observable; add the §10 row with a trigger. Explicitly state `Restore` is not a ceiling check and that lowering the cap between resumes is a supported stop.

### H-5. The feasibility check is undefined where it matters, and on `--resume` it converts exit 2 into exit 1.

Three holes:

1. **`f` is never given a value.** With cap $5.00 and pess $0.0328: `f=0.5` → `N' = 76`, the check never fires at concurrency 8; `f=0.05` → `N' = 7`, it fires for no benefit. The behavior of the entire mechanism is a free parameter.
2. **Resume.** The check must run against `cap − spent`, i.e. **after** `Guard.Restore` at `core/baseline.go:212`, not against `cap`. The plan calls it a "startup" check and says nothing about placement. This is verbatim the defect the plan itself diagnosed for the confirmation prompt (H-D item 2: *"it could not be computed on resume… the completed-Case set is loaded inside `core.Baseline`"*) — diagnosed, fixed for §2.4, and not applied to the check it invented in the same section.
3. **Exit code.** Today, a resume with an exhausted cap starts, the first `Authorize` is denied, `IsFatal` fires (`core/baseline.go:256`), status is `BUDGET_STOPPED`, exit **2** (`errs.ExitBudgetStopped`) — "resumable, nothing is wrong with the data". If the feasibility check refuses at startup with `ErrInvalidInput`, the same situation exits **1**: "broken build". `errs.go:11-13` calls exit codes *"a covenant after 1.0: CI gates branch on the difference"*. The plan does not name the sentinel the refusal uses.

Also unaddressed: reducing concurrency does nothing when `pessimistic` is itself wrong (unknown model, stale price table) — the check's input is the same number whose error it cannot see. And the *forfeiture* (`1 − N×pess/cap`, up to 20% at concurrency 32 by my measurement) is never stated to the user anywhere, though §9 sends the overshoot bound to `docs/mental-model.md`.

**Fix shape:** pick `f` with a written rationale; compute against remaining headroom after `Restore`; refuse with `ErrBudgetExceeded` (exit 2, resumable) not `ErrInvalidInput`; state the forfeiture bound in `mental-model.md` alongside the overshoot bound.

### H-7. §2.8 and §6 give contradictory security rules for loopback/RFC1918, and the per-host key normalization is undefined and non-injective.

**(a) Contradiction.** §2.8: *"Refuse loopback, link-local (`169.254.169.254`), and RFC1918 base URLs **unless opted in** — SSRF from a CI runner with an instance-metadata endpoint is a credential-theft primitive."* §6, two rows: *"Base URL at loopback / RFC1918, no credential | **Allowed.** §2.8's own principle is that destination matters because a key travels; no key, no question."* An implementer has two contradictory specs for a security control in one document, and §6's reasoning is wrong on its own terms: SSRF's other harm is using Kno as a request proxy into an internal network, where the response body lands in `Response.output` and is persisted as a trace. That harm is credential-independent.

**(b) Normalization.** `KNO_API_KEY_<NORMALIZED_HOST>` — the plan never defines `NORMALIZED_HOST`. Env var names permit `[A-Za-z0-9_]`, so any mapping from DNS names collapses characters. Concretely: `api.groq.com`, `api-groq-com`, and `api_groq_com` all normalize to `API_GROQ_COM`. An attacker registering the typosquat `api-groq.com` receives the key the user bound to `api.groq.com`, with **no flag involved** — §2.8's own threat #1, reached through the mechanism §2.8 introduces to prevent it. Ports (`localhost:8000` vs `localhost_8000`), trailing dots, case, and punycode are all unspecified. And the user cannot guess the name.

**Fix shape:** stop deriving env var names from hosts. Take an explicit binding — `--key-env api.groq.com=GROQ_API_KEY` (the *name* of a variable is not a secret, so this does not violate the no-keys-in-flags rule) or a `kno.yaml`/`KNO_API_KEYS` map. If a derived form is kept, require an injective encoding and refuse at startup when two configured hosts collide. Pick one of §2.8/§6 for loopback/RFC1918 and delete the other.
